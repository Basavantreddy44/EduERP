# Database Design: Entity & Relationship Plan

Baseline: **[DOC §9–10]** conventions are adopted in full. This file is a **plan**: executable migrations are written per phase. Field-level definitions go to [DATA_DICTIONARY.md](DATA_DICTIONARY.md).

## 1. Conventions [DOC §9]

| Item | Standard |
|---|---|
| PK | `id UUID` (UUIDv7 generated by the application, for index locality) |
| Tenant | `tenant_id UUID NOT NULL` + `UNIQUE(tenant_id, id)` on every tenant-owned table |
| Campus | `campus_id` where campus-specific; nullable only when truly tenant-wide |
| Legal entity | `legal_entity_id` on all financial tables [ENH G-01] |
| Naming | snake_case plural tables; Prisma models PascalCase with `@@map` |
| Time | `TIMESTAMPTZ` for instants; `DATE` for business dates; timezone on campus |
| Money | `NUMERIC(19,4)` + `currency_code CHAR(3)`; app uses decimal.js `Money`, never JS `number` |
| Percent | `NUMERIC(7,4)` |
| Audit columns | `created_at, created_by, updated_at, updated_by, version INT` (optimistic lock) |
| Status | Postgres enums or CHECK constraints, mirrored in `packages/contracts` |
| Deletion | `archived_at` for reversible masters only. **No DELETE grants on posted/published/audit tables** (enforced by role grants + triggers) |
| History | Effective-dated rows (`effective_from`, `effective_to`) or append-only events |
| Human numbers | Separate `*_number` columns allocated by the numbering service, unique per scope |

## 3. Key relationships [DOC §9 "Important entity relationships"] + additions

- Tenant 1–N legal_entities 1–N campuses. Campus 1–N departments, rooms, student_groups, employees (primary campus).
- users N–N tenants via user_tenants. Membership 1–N user_roles (role + scope: tenant | campus | department | group).
- students N–N guardians via student_guardians (relationship, is_primary, access_scope JSON → **normalised flags**: can_view_academics, can_view_fees, can_pay, can_pickup, custody_restricted, verified_at).
- student 1–N student_enrollments → (academic_year, campus, programme_level, student_group). **Partial unique index**: `UNIQUE (tenant_id, student_id, academic_year_id) WHERE status = 'ACTIVE'`.
- course_offering = course × student_group × term (× faculty via faculty_assignments). Timetable entries reference offering + room + slot. Attendance sessions reference offering (period mode) or group (daily mode).
- Exam 1–N exam_subjects (→ assessment components). Marks reference (registration, component, examiner). student_results reference result_calculation_version.
- fee_invoice 1–N lines; payments N–N invoice lines via payment_allocations; receipt 1–1 confirmed payment (or instrument clearance); gateway transactions 1–N per payment order.
- journal_entry 1–N lines; `source_type, source_id` unique per posting purpose (idempotent posting).
- PO 1–N lines; GRN lines reference PO lines (partial receipts; ordered/received/accepted/rejected qty).
- vehicle_trip 1–N gps_location_logs and trip_attendance events.

## 4. Academic structure model (G-14, DEC-13)

```
education_boards/universities ─┐
programs (CBSE-K12 / B.Tech CSE / BSc Physics) ── program_levels (Grade 6 | Semester 3)  [ordered]
        │                                               │
        └─ curriculum_items (level × course, credits, mandatory/elective, assessment scheme)
student_groups (type: SECTION | BATCH | COHORT | ELECTIVE_GROUP | LAB_BATCH; level; year; campus)
course_offerings (course × group × term)  ── faculty_assignments (role: primary/co/lab)
student_enrollments → (program_level, primary student_group); group_memberships → elective/lab groups
```
School = program "Primary/Secondary (Board X)", levels = grades, groups = sections. College = program "B.Tech CSE", levels = semesters, groups = batches/divisions, plus elective groups. The UI labels come from **institution-type templates** (Class/Section vs Semester/Batch).

## 5. Integrity rules [DOC §10]

- Tenant-composite FKs everywhere (Architecture §3.5).
- `CHECK (debit >= 0 AND credit >= 0 AND (debit = 0) <> (credit = 0))` on journal lines. Balance check in a deferred constraint trigger on posting + in the application.
- Trigger blocking UPDATE/DELETE of `journal_entries`/`lines` where status = POSTED (except the reversal link column), the same for receipts and published results, and append-only `audit_logs`.
- Unique `(tenant_id, provider, provider_event_id)` on webhook events. Unique `(tenant_id, idempotency_key, endpoint)`.
- Exclusion constraints (`btree_gist`) for room/teacher/vehicle overlaps where the timetable/trip model allows. Otherwise conflict queries in a serialisable section.
- Invoice totals reproducible: lines store unit amount, qty, discount, tax code, tax amount, rounding policy version.

## 6. Indexing & partitioning

Tenant-leading composite indexes `(tenant_id, campus_id, academic_year_id, ...)`. Partial indexes for active/open/unposted rows. `pg_trgm` + `tsvector` for name/number search. Monthly range partitioning for audit_logs, gps_location_logs, notification_deliveries and attendance_device_logs once volumes justify it (retention defined first [DOC §10]). Verify with `EXPLAIN (ANALYZE)` on seeded volume data.

## 7. Migration discipline [DOC §10]

Prisma migrations + hand-edited SQL. Never edit an applied migration. Expand-and-contract for breaking changes. Every migration is tested on CI against an empty DB **and** a seeded DB. RLS policy presence is asserted by a test that lists all tables with `tenant_id` and fails if any lack `FORCE ROW LEVEL SECURITY` + a policy. Seeds contain only reference data and role templates. Synthetic demo data lives in a separate, never-in-production seeder.
